## Context

Der Event-Wizard Step 5 ("Buchung") startet mit einer leeren Buchungsoptionen-Liste. Der Nutzer muss manuell einen Buchungstyp anlegen. Laut bestehender Spec `event-smart-defaults` soll bereits ein Default-Buchungstyp basierend auf der Event-Dauer vorausgefüllt werden ("Standard", `Tage × 10€`). Diese Anforderung wird jetzt mit einem Tagespreis von 15€ (statt 10€) umgesetzt.

Betroffene Dateien:
- `frontend/src/store/eventWizardStore.ts` — Logik für Default-Buchungstyp
- `frontend/src/components/events/wizard/StepBookingOptions.tsx` — UI muss vorausgefüllte Option handhaben
- `frontend/src/schemas/eventWizard.ts` — ggf. `is_auto_generated` Flag

## Goals / Non-Goals

**Goals:**
- Wenn Start- und Enddatum gesetzt sind, wird automatisch ein Buchungstyp vorausgefüllt
- Name: "Teilnahme", Preis: `Anzahl Tage × 15€`
- Nutzer kann den vorausgefüllten Typ bearbeiten oder löschen
- Bearbeitung markiert den Typ als manuell (keine weiteren Auto-Updates)

**Non-Goals:**
- Kein Backend-Änderung (Buchungsoptionen werden über den bestehenden Payload erstellt)
- Kein neues Model-Feld
- Keine Änderung an bestehenden Buchungsoptionen-APIs

## Decisions

### 1. Berechnung im Store, nicht in der Komponente

Die Default-Buchungstyp-Berechnung passiert im Zustand Store (`eventWizardStore.ts`), getriggert wenn `start_date` oder `end_date` über `updateStep3()` gesetzt werden. Grund: Die Daten aus Step 3 müssen in Step 5 reflektiert werden — der Store ist der richtige Ort für cross-step Logik.

Alternative: Berechnung in `StepBookingOptions` per `useEffect` — abgelehnt, weil die Komponente evtl. noch nicht gemountet ist wenn Step 3 ausgefüllt wird.

### 2. Tracking via `_isAutoGenerated` Flag

Jede Wizard-BookingOption bekommt ein internes `_isAutoGenerated: boolean` Flag (nicht an Backend gesendet). Wenn der Nutzer die Option editiert, wird das Flag auf `false` gesetzt. Auto-Updates (bei Datumsänderung) überschreiben nur Optionen mit `_isAutoGenerated: true`.

### 3. 15€ pro Tag, inklusive Start- und Endtag

Tage-Berechnung: `differenceInCalendarDays(end_date, start_date) + 1` (beide Tage inklusive). Bei fehlendem End-Datum wird 1 Tag angenommen. Preis = `Tage × 15`.

## Risks / Trade-offs

- [Nutzer ändert Datum nach Step 5 Bearbeitung] → Auto-generierte Option wird aktualisiert, manuell bearbeitete nicht. Klar durch `_isAutoGenerated` Flag.
- [Kein Datum gesetzt] → Kein Default-Buchungstyp wird erstellt. Step 5 bleibt leer.

**Keine API-Änderungen, keine Schema-Änderungen, keine Migrationen.**
